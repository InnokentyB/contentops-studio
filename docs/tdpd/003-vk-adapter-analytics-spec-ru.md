# TDPD-003: VK-адаптер публикации и аналитики

Статус: draft for product approval
Режим: TDPD Plan
Метод: Test-Driven Product Development (TDPD), оригинальный метод Иннокентия Бодрова
Версия: 0.1
Дата: 2026-08-11

## 1. Бизнес-проблема

Планнер уже умеет публиковать записи во VK и получать публичные счётчики записи, но этого недостаточно для оценки дистрибуции. Владелец проекта не видит подписной, вирусный и рекламный охват, переходы, вступления, скрытия, жалобы и отписки, а недельные изменения приходится считать вручную.

Нужен единый наблюдаемый контур, в котором публикация VK связана с ежедневными неизменяемыми снимками метрик, а недельный замер рассчитывается из сохранённых данных без ручного копирования.

### Акторы

- владелец проекта, который подключает сообщество и проводит приёмку (UAT);
- редактор, который публикует и изучает результат;
- планнер, который хранит связь задачи с VK-записью и снимки аналитики;
- VK API как внешний источник данных;
- планировщик времени, который запускает ежедневный сбор.

### Сигналы успеха

- 100% опубликованных через адаптер VK задач получают стабильные `owner_id`, `post_id` и permalink;
- для доступных VK API данных ежедневный снимок создаётся не более одного раза за логическую дату сбора;
- недельный отчёт показывает начальное, конечное и дельту каждого накопительного показателя;
- частичная недоступность `stats.getPostReach` не уничтожает и не обнуляет данные `wall.getById`;
- пользователь видит причину отсутствия расширенной статистики и следующее действие, а не нулевые значения;
- повторный запуск одного сбора не создаёт дубли снимков.

## 2. Подтверждённый внешний контракт

Источник истины для метода и полей: официальная JSON Schema VK API 5.199.

- `wall.getById` используется для текста, даты и публичных счётчиков записи: просмотры, лайки, репосты и комментарии.
- `stats.getPostReach` используется для внутренней статистики записи.
- `stats.getPostReach.owner_id` передаётся как отрицательный ID сообщества.
- `stats.getPostReach.post_ids` содержит от одного до 30 положительных ID записей.
- `stats.getPostReach` в схеме имеет `access_token_type: user`. Токен публикации сообщества нельзя молча считать подходящим для расширенной аналитики.
- Ответ `stats.getPostReach` может содержать `reach_total`, `reach_subscribers`, `reach_viral`, `reach_ads`, `links`, `to_group`, `join_group`, `hide`, `report`, `unsubscribe` и `sex_age`.

Ссылки:

- https://github.com/VKCOM/vk-api-schema/blob/master/stats/methods.json
- https://github.com/VKCOM/vk-api-schema/blob/master/stats/objects.json

## 3. Граница продукта

### Входит в слайс

- проверка подключения VK до первой публикации;
- публикация текста и необязательного изображения;
- сохранение `owner_id`, `post_id` и permalink;
- базовый сбор через `wall.getById`;
- расширенный сбор через `stats.getPostReach` пачками до 30 записей;
- ручной запуск сбора для одной публикации;
- ежедневный автоматический сбор для активного окна наблюдения;
- неизменяемые снимки метрик;
- недельная дельта и признак неполных данных;
- экспорт выбранного диапазона в JSON и CSV;
- понятные состояния токена, прав, rate limit и удалённой записи.

### Не входит в первый слайс

- аналитика рекламных кабинетов вне полей `stats.getPostReach`;
- демографические отчёты глубже сохранения полученного `sex_age`;
- автоматические продуктовые рекомендации по контенту;
- удаление или редактирование уже опубликованной записи через планнер;
- подмена отсутствующих метрик нулями;
- использование CSV/JSON как основного хранилища.

## 4. Архитектурная граница для согласования

### Конфигурация канала

VK-канал хранит раздельные полномочия:

- `vk_id` — ID сообщества; нормализуется к отрицательному `owner_id`;
- `publish_access_token` — токен, используемый только для публикации и загрузки медиа;
- `stats_access_token` — пользовательский токен для `stats.getPostReach`;
- `api_version` — фиксированная поддерживаемая версия, первоначально `5.199`;
- `analytics_enabled` — явное включение расширенного сбора.

Для обратной совместимости существующий `api_key` временно читается как `publish_access_token`. Он не должен автоматически использоваться как `stats_access_token` после миграции.

Секреты не возвращаются API/UI/MCP после сохранения и не попадают в логи. UI показывает только наличие токена и результат последней проверки.

### Идентичность публикации

После успешного `wall.post` задача сохраняет структурированные поля:

- `provider = vk`;
- `owner_id`;
- `post_id`;
- `published_link`;
- `published_at`;
- `channel_id` и `publication_task_id`.

Парсинг `post_id` из permalink допустим только для старых данных. Для новых публикаций API-идентификаторы сохраняются напрямую.

### Снимок метрик

Основное хранилище — база планнера. Снимок неизменяем и содержит:

- идентичность проекта, канала и публикационной задачи;
- `provider`, `owner_id`, `post_id`;
- `captured_at` и `logical_date` в timezone проекта;
- публичные метрики `views`, `likes`, `comments`, `reposts`;
- расширенные метрики `reach_total`, `reach_subscribers`, `reach_viral`, `reach_ads`, `links`, `to_group`, `join_group`, `hide`, `report`, `unsubscribe`;
- `wall_status` и `reach_status`: `collected`, `unavailable`, `forbidden`, `not_found`, `rate_limited`, `failed`;
- provider error code без токена и чувствительного payload;
- сырой нормализованный JSON для совместимости с новыми полями VK.

Уникальность: один автоматический снимок на `publication_task_id + logical_date + collection_mode`. Ручной повтор обновляет незавершённый снимок этой даты либо создаёт отдельный снимок с явным `collection_mode = manual`, решение требуется подтвердить до реализации.

### Период наблюдения

Предлагаемый default: ежедневно собирать метрики 30 дней после публикации. После этого — только вручную или в день недельного/месячного замера. Период должен быть настройкой проекта, а не константой адаптера.

## 5. Детерминированные правила

### R-VK-001 — отсутствие расширенного токена

Если настроен только токен публикации, публикация и `wall.getById` продолжают работать. `stats.getPostReach` получает состояние `unavailable`, а UI предлагает подключить расширенную аналитику.

### R-VK-002 — частичный результат

Успех одного VK-метода сохраняется независимо от ошибки второго. Ошибка не превращает неизвестные показатели в `0` и не перезаписывает предыдущий снимок.

### R-VK-003 — пачки

Расширенная аналитика группируется по `owner_id`; каждая API-команда содержит не более 30 `post_ids`. Результат сопоставляется по `post_id`, а не по позиции в массиве.

### R-VK-004 — идемпотентность

Повтор одного планового запуска за логическую дату не создаёт второй автоматический снимок и не удваивает недельные значения.

### R-VK-005 — неизменность публикации

Сбор аналитики не меняет текст, статус публикации, permalink, дату публикации или подтверждённый контент. MCP и импорт плана не могут откатить опубликованную задачу.

### R-VK-006 — недельная дельта

Для накопительных метрик недельная дельта равна `последний доступный снимок периода − последний доступный снимок до начала периода`. Отчёт показывает обе точки и время их получения.

Если начальной или конечной точки нет, дельта имеет `null`, а отчёт помечается `incomplete`; нулём отсутствие данных не считается.

### R-VK-007 — удалённая или недоступная запись

Если запись удалена, закрыта или токен потерял доступ, существующая история сохраняется. Новая попытка фиксирует причину и доступное следующее действие.

### R-VK-008 — экспорт

CSV и JSON формируются из сохранённых снимков выбранного проекта и диапазона дат. Экспорт не обращается к VK API и не раскрывает channel config или токены.

## 6. Пользовательские сценарии

### SC-VK-001 — подключение с полной аналитикой

**Начальное состояние:** владелец проекта имеет VK-сообщество, токен публикации и пользовательский токен статистики.
**Действие:** сохраняет канал и запускает проверку подключения.
**Наблюдаемый результат:** отдельно подтверждены публикация, базовые метрики и расширенная аналитика; токены после сохранения замаскированы.
**Критерий:** канал имеет `ready_to_publish = true` и `extended_analytics = ready`.

### SC-VK-002 — подключение только для публикации

**Начальное состояние:** указан `vk_id` и рабочий токен публикации, токена статистики нет.
**Действие:** владелец проверяет канал.
**Наблюдаемый результат:** публикация доступна, расширенная аналитика обозначена как не подключённая.
**Критерий:** система не блокирует публикацию и не обещает reach-метрики.

### SC-VK-003 — публикация фиксирует стабильную идентичность

**Начальное состояние:** канал готов к публикации, задача содержит текст.
**Действие:** редактор нажимает «Опубликовать сейчас».
**Наблюдаемый результат:** пост появляется в сообществе; задача получает `owner_id`, `post_id`, permalink и статус `published`.
**Критерий:** повторное обновление плана не меняет опубликованную задачу и не создаёт второй пост.

### SC-VK-004 — публикация изображения с безопасным fallback

**Начальное состояние:** задача содержит текст и изображение.
**Действие:** адаптер публикует запись.
**Наблюдаемый результат:** при успешной загрузке публикуются текст и изображение; при ошибке загрузки пользователь видит предупреждение и явно выбирает публикацию только текста либо повтор.
**Критерий:** адаптер не публикует тихо неполную запись без зафиксированного решения.

### SC-VK-005 — ручной полный сбор одной записи

**Начальное состояние:** опубликованная задача имеет оба токена.
**Действие:** пользователь нажимает «Обновить метрики».
**Наблюдаемый результат:** `wall.getById` и `stats.getPostReach` выполняются; UI показывает публичные и внутренние показатели с временем снимка.
**Критерий:** снимок связан с выбранной задачей и доступен после перезагрузки.

### SC-VK-006 — ежедневный сбор пачками

**Начальное состояние:** в одном сообществе наблюдается 65 публикаций.
**Внешнее событие:** наступает время ежедневного запуска.
**Наблюдаемый результат:** расширенная статистика запрашивается тремя пачками `30 + 30 + 5`; для каждой записи создаётся один снимок.
**Критерий:** ни один запрос не содержит больше 30 ID, результаты привязаны по `post_id`.

### SC-VK-007 — повтор ежедневного запуска

**Начальное состояние:** автоматический снимок за текущую логическую дату уже сохранён.
**Внешнее событие:** worker повторно получает ту же задачу после retry.
**Наблюдаемый результат:** второй снимок не создаётся; существующая завершённая запись остаётся неизменной.
**Критерий:** количество автоматических снимков за дату равно числу уникальных публикаций.

### SC-VK-008 — `stats.getPostReach` запрещён, `wall.getById` доступен

**Начальное состояние:** токен статистики просрочен или не имеет нужного доступа.
**Действие:** запускается сбор.
**Наблюдаемый результат:** просмотры, лайки, комментарии и репосты сохранены; reach-поля имеют `null`, `reach_status = forbidden`; UI показывает способ переподключения.
**Критерий:** базовые данные не теряются и не помечаются ошибочными.

### SC-VK-009 — временный rate limit и retry

**Начальное состояние:** VK возвращает ограничение частоты для одной пачки.
**Внешнее событие:** worker выполняет ежедневный сбор.
**Наблюдаемый результат:** применяется ограниченный retry с backoff; другие сообщества и готовые пачки продолжают обрабатываться.
**Критерий:** после исчерпания retry фиксируется `rate_limited` и следующая допустимая попытка, процесс не создаёт цикл запросов.

### SC-VK-010 — запись удалена после публикации

**Начальное состояние:** у задачи есть исторические снимки, запись удалена во VK.
**Действие:** запускается новый сбор.
**Наблюдаемый результат:** история остаётся доступной; новый результат имеет `not_found`; задача остаётся опубликованной с отдельным live-status записи.
**Критерий:** публикационный статус не откатывается в `planned` или `failed`.

### SC-VK-011 — недельная дельта

**Начальное состояние:** имеются снимки до начала и в конце недели.
**Действие:** пользователь открывает недельный отчёт.
**Наблюдаемый результат:** для каждого накопительного показателя видны начальное значение, конечное значение и дельта; рядом показаны timestamp обеих точек.
**Критерий:** расчёт воспроизводим из сохранённых снимков без вызова VK API.

### SC-VK-012 — неполная неделя

**Начальное состояние:** отсутствует снимок до начала недели либо нет конечного снимка.
**Действие:** пользователь открывает недельный отчёт.
**Наблюдаемый результат:** доступные абсолютные значения показаны, дельта отсутствующего интервала равна `null`, отчёт помечен `incomplete`.
**Критерий:** UI не показывает ложной нулевой динамики.

### SC-VK-013 — экспорт снимков

**Начальное состояние:** проект содержит VK-снимки за выбранную неделю.
**Действие:** пользователь экспортирует JSON или CSV.
**Наблюдаемый результат:** файл содержит идентичность публикации, timestamps, статусы и метрики только выбранного проекта и периода.
**Критерий:** экспорт воспроизводит данные UI и не содержит токенов.

### SC-VK-014 — изоляция проектов

**Начальное состояние:** пользователь имеет доступ к проекту A, но не к проекту B.
**Действие:** запрашивает снимки или экспорт публикации проекта B по известному ID.
**Наблюдаемый результат:** система не раскрывает наличие публикации, метрики или настройки канала.
**Критерий:** ответ эквивалентен отсутствующему ресурсу, audit log не содержит токен.

### SC-VK-015 — числовой счётчик уменьшился

**Начальное состояние:** VK вернул значение накопительного показателя ниже предыдущего снимка из-за модерации или пересчёта.
**Действие:** строится недельная дельта.
**Наблюдаемый результат:** отрицательная дельта сохраняется как факт и помечается `provider_adjustment`; система не заменяет её нулём.
**Критерий:** исходные снимки и вычисление доступны для аудита.

## 8. Ручная приёмка (UAT)

1. Владелец подключает тестовое VK-сообщество и видит три независимых capability: публикация, публичные метрики, расширенная аналитика.
2. Публикует тестовую запись с изображением и проверяет совпадение текста, медиа и permalink.
3. Запускает ручной сбор и сверяет минимум одну запись с интерфейсом статистики VK.
4. Повторяет сбор и убеждается, что история снимков объяснима, а данные не дублируются.
5. Открывает недельный отчёт и вручную проверяет одну дельту по двум снимкам.
6. Отключает токен статистики и убеждается, что публикация и публичные счётчики продолжают работать.
7. Экспортирует CSV и JSON и проверяет отсутствие секретов.

## 9. Открытые решения до Red Gate

1. Подтвердить период ежедневного наблюдения: предлагается 30 дней.
2. Подтвердить семантику ручного снимка в дату, когда автоматический уже существует: отдельная история или обновление незавершённого снимка.
3. Подтвердить, нужен ли первый слайс `sex_age` в UI или достаточно сохранить raw normalized JSON.
4. Выбрать UX ошибки изображения: обязательное подтверждение публикации без изображения либо автоматический fallback с последующим предупреждением. Рекомендуется явное подтверждение.
5. Подтвердить хранение токенов: существующий JSON config недостаточен без гарантированного шифрования/secret storage.
6. Определить срок хранения снимков и политику удаления при архивировании проекта.
