# TDPD-005: Изоляция недельных пакетов при delta-импорте

Статус: approved for combined RED phase  
Режим: TDPD Deliver (совместно с TDPD-004)  
Версия: 0.1  
Дата: 2026-08-17  
Инцидент: `delta_safe`-импорт W11 изменил пакет, к которому был привязан весь архив проекта

## 1. Результат, который нужен пользователю

Добавление публикаций новой недели не должно возвращать в активную очередь задачи прошлых недель, менять их недельную принадлежность или создавать впечатление, что у опубликованных материалов пропали текст и ссылка.

После импорта дельты пользователь должен видеть:

- прежние недели без изменений;
- новую неделю только с задачами, относящимися к её периоду;
- опубликованные и снятые задачи только в истории или по явному фильтру;
- сохранённые текст, permalink, outcome, метрики и историю публикации;
- понятный отчёт: какой пакет создан или переиспользован и какие задачи затронуты.

## 2. Фактический инцидент 17.08.2026

В проект 10 был передан `delta_safe`-план на 17–23.08:

- `incomingActions = 13`;
- `processedActions = 13`;
- `deletedStaleTasks = 0`.

Импорт не создал дубль контрольной задачи Threads №643 и не удалил её runtime-данные. Однако единственный `WeekPackage` №38 был обновлён с новой рамкой 17–23.08. К нему уже были привязаны все импортированные материалы проекта, поэтому новый недельный пакет фактически содержал 293 материала с датами от июня до сентября.

При расследовании обнаружились **два независимых дефекта**, которые визуально выглядели одинаково.

Дефект A — пакет основного проекта:

- пакет №38 основного проекта был обновлён рамкой W11;
- к нему уже были привязаны 293 материала разных периодов;
- недельная проекция перестала быть изолированной.

Дефект B — сохранённый выбор архивного проекта:

- UI продолжал держать выбранным архивный проект №15 `analystcraft-w10-2026-08-10`;
- этот проект был архивирован 09.08, но оставался доступен владельцу и сохранён в browser state;
- в нём находились 25 старых задач-заготовок без runtime-результатов;
- показанная пользователем задача Сетки была №622 из проекта №15: `awaiting_manual_publication`, empty, без permalink;
- соответствующие реальные публикации основного проекта №10 имели другие ID и отдельное runtime-состояние.

Наблюдаемое проявление в UI:

- публикации прошлой недели появились в активном списке;
- старая заготовка из архивного проекта выглядела как потерявшая данные опубликованная задача основного проекта;
- редактор выглядел пустым;
- форма подтверждения выглядела так, будто permalink отсутствует;
- пользователь не мог отличить дубль от потери публикационного результата.

Контрольная серверная проверка похожей задачи №643 в основном проекте показала:

- ID остался `643`;
- `status = published`;
- `publication_outcome = published`;
- `published_link = https://www.threads.com/share/E0lHQv3Km/`;
- полное тело оставалось в `quality_report.handoff_bundle.publication.body` и resource snapshot;
- runtime основного проекта не был потерян; интерфейс показывал другой проект с похожими названиями задач.

## 3. Корневая причина

### 3.1. Пакет выбирается без учёта периода

В `PublicationPlanService` используется первый пакет проекта:

```ts
const existingWeekPackage = await tx.weekPackage.findFirst({
    where: { project_id: project.id },
    orderBy: { id: 'asc' }
});
```

Затем этот пакет обновляется данными любого следующего импорта:

```ts
await tx.weekPackage.update({
    where: { id: existingWeekPackage.id },
    data: weekPackageData
});
```

Таким образом `WeekPackage` используется как изменяемая глобальная настройка проекта, хотя модель и UI трактуют его как снимок конкретной недели.

### 3.2. У пакета нет защищённой идентичности

В схеме отсутствует уникальность по проекту и периоду. Поля `plan_id` и `plan_version` существуют, но импорт их не заполняет в `weekPackageData`. Нет правила, запрещающего менять `week_start/week_end` у пакета, к которому уже привязаны материалы.

### 3.3. `active` включает опубликованные задачи

Серверный фильтр `/api/publication-tasks?status=active` включает `published`. Скрытие опубликованных реализовано только во frontend. Ошибка проекции, stale cache или несовпадение list/detail превращают завершённые задачи в видимый активный долг.

### 3.4. Состояние публикации хранится в нескольких слоях

UI должен согласовать:

- `ContentItem.status`;
- `ContentItem.published_link`;
- `quality_report.publication_outcome`;
- `metrics.publication_outcome`;
- `quality_report.handoff_bundle.publication.body`;
- `draft_text`;
- resource snapshots.

Если список и детальная карточка читают разные слои или разные версии ответа, опубликованная задача может выглядеть пустой, хотя runtime-данные сохранились.

### 3.5. Архивный проект может оставаться текущим

Архивация проекта не отзывает membership. Если frontend хранит `currentProject` локально, уже выбранный архивный проект продолжает открываться после архивации. Название проекта показано второстепенно, поэтому пользователь воспринимает похожие задачи как задачи основного проекта.

Приложение должно проверять доступность и `is_archived` сохранённого проекта при старте и после обновления списка проектов. Архивный проект нельзя автоматически оставлять текущим рабочим контекстом.

## 4. Инварианты

### R-WPI-001 — пакет соответствует одному периоду

`WeekPackage` принадлежит ровно одному проекту и одному закрытому диапазону дат. После появления первой связанной задачи `week_start` и `week_end` нельзя менять обычным импортом.

### R-WPI-002 — точное разрешение пакета

Импорт ищет пакет по:

```text
project_id + normalized week_start + normalized week_end
```

Допускается дополнительная проверка `plan_id/plan_version`, но нельзя выбирать пакет только по `project_id`, минимальному ID или максимальному ID.

### R-WPI-003 — новая неделя создаёт новый пакет

Если точного периода нет, создаётся новый `WeekPackage`. Предыдущие пакеты не обновляются.

### R-WPI-004 — дельта затрагивает только входящие действия

В режиме `delta_safe`:

- создаются или обновляются только `incomingActions`;
- только новые задачи получают пакет целевой недели;
- существующая задача может получить другой пакет лишь через отдельную явную операцию переноса;
- отсутствие задачи во входящей дельте ничего с ней не делает.

### R-WPI-005 — опубликованный runtime неизменяем импортом

Для задачи, у которой выполняется хотя бы одно условие:

- `status = published`;
- есть `published_link`;
- есть подтверждённый publication outcome;
- существует `PublicationFact` после реализации TDPD-004,

импорт не меняет:

- `week_package_id`;
- статус и content state;
- тело, revision и resource snapshot;
- permalink;
- outcome;
- фактическое время выхода;
- метрики и checkpoints.

### R-WPI-006 — конфликт ID между неделями останавливается

Если входящее действие имеет тот же внешний `task_id/item_key`, что существующая задача другой недели, импорт возвращает конфликт `CROSS_CYCLE_TASK_ID` и не изменяет задачу. Автоматически переносить её нельзя.

### R-WPI-007 — активность определяется на сервере

`status=active` по умолчанию исключает:

- `published`;
- `cancelled/skipped`;
- `publication_outcome = removed/blocked/restricted`, если workflow завершён;
- задачи вне выбранной недели, когда передан `weekPackageId` или диапазон.

История доступна отдельным фильтром. Клиентское скрытие остаётся дополнительной защитой, а не единственным фильтром.

### R-WPI-008 — опубликованное всегда выглядит опубликованным

Если канонический предикат публикации истинен, list и detail endpoints возвращают:

- `content_state = published`;
- непустой `published_link`, если permalink поддерживается;
- сохранённое тело из канонического источника;
- недоступные кнопки повторной публикации;
- читаемый блок результата вместо пустого редактора как основного состояния.

### R-WPI-009 — импорт сообщает реальный blast radius

Ответ импорта содержит:

- `targetWeekPackageId`;
- `createdWeekPackage`;
- `incomingActions`;
- `createdTasks`;
- `updatedTasks`;
- `movedTasks`;
- `runtimeLockedTasksSkipped`;
- `conflicts`;
- `unchangedTasks`;
- `previousPackagesUpdated` — всегда `0` для `delta_safe`.

### R-WPI-010 — операция идемпотентна

Повтор той же дельты с тем же idempotency key не создаёт новый пакет и новые задачи, не меняет runtime и возвращает тот же логический результат.

### R-WPI-011 — архивный проект не может быть активным контекстом

Если сохранённый `currentProject` архивирован, недоступен пользователю или отсутствует в активном списке, frontend очищает выбор и переключается на доступный активный проект либо показывает явный экран выбора. API по умолчанию не возвращает архивные проекты в рабочем списке.

Заголовок рабочей области всегда показывает имя и ID проекта достаточно заметно, чтобы различить основной проект и архивный дубль.

## 5. Предлагаемая модель

### 5.1. Уникальность недели

Добавить нормализованные даты и уникальный индекс:

```prisma
@@unique([project_id, week_start, week_end])
```

Перед миграцией проверить существующие конфликты. Если в одном проекте законно нужны версии одной недели, использовать отдельную сущность версии или уникальность:

```text
project_id + week_start + week_end + plan_version
```

При этом должна существовать ровно одна активная версия недели.

Решение владельца от 17.08.2026 для первого слайса: идентичность пакета — строго
`project_id + week_start + week_end`. `plan_version` хранится как метаданные и не
участвует в уникальности. Версионирование одной недели откладывается до появления
подтверждённого пользовательского сценария. Перенос между неделями остаётся отдельной
аудируемой командой.

### 5.2. Разделить создание и изменение

Нужны отдельные операции:

- `resolveOrCreateWeekPackage(projectId, cycleStart, cycleEnd, metadata)`;
- `updateWeekPackageMetadata(packageId, metadata)` — не меняет период;
- `moveContentItemToWeekPackage(...)` — отдельная аудируемая команда с причиной;
- `importPlanDelta(...)` — не вызывает неявный move для существующих задач.

### 5.3. Явный контекст чтения

Добавить к API списка:

```text
GET /api/publication-tasks?status=active&weekPackageId=50
```

или:

```text
GET /api/publication-tasks?status=active&from=2026-08-17&to=2026-08-23
```

UI текущей недели не должен строиться из всех задач проекта.

## 6. Сценарии

### SC-WPI-001 — первая неделя проекта

**Дано:** пакетов нет.  
**Когда:** импортируется W10.  
**Тогда:** создаётся один пакет W10; все входящие задачи связаны с ним.

### SC-WPI-002 — следующая неделя дельтой

**Дано:** W10 содержит опубликованные и незавершённые задачи.  
**Когда:** импортируются 13 действий W11 в `delta_safe`.  
**Тогда:** создаётся пакет W11; W10 и его задачи байт-в-байт не меняются; в W11 находятся только 13 входящих действий либо явно существующие задачи того же периода.

### SC-WPI-003 — повтор W11

**Дано:** пакет W11 уже создан.  
**Когда:** повторяется та же дельта.  
**Тогда:** пакет переиспользуется, новых задач нет, runtime не меняется.

### SC-WPI-004 — опубликованный ID пришёл в новой неделе

**Дано:** `task_id=w10-01`, status published, permalink сохранён.  
**Когда:** W11 содержит действие с `id=w10-01`.  
**Тогда:** импорт возвращает `CROSS_CYCLE_TASK_ID`; задача W10 не меняется.

### SC-WPI-005 — правка незавершённой задачи той же недели

**Дано:** planned-задача W11.  
**Когда:** дельта W11 меняет её время и brief.  
**Тогда:** задача обновляется внутри W11; ID и пакет сохраняются.

### SC-WPI-006 — активная очередь

**Дано:** W10 опубликована, W11 запланирована.  
**Когда:** UI запрашивает active W11.  
**Тогда:** возвращаются только незавершённые W11; опубликованная W10 отсутствует.

### SC-WPI-007 — согласованность list/detail

**Дано:** опубликованная задача с телом в handoff bundle и permalink.  
**Когда:** запрашиваются list и detail.  
**Тогда:** оба возвращают `published`; detail показывает тело и ссылку; пустой `draft_text` не понижает состояние до empty.

### SC-WPI-008 — аварийное восстановление

**Дано:** пакет ошибочно сменил период и захватил архив.  
**Когда:** оператор запускает repair с preview.  
**Тогда:** preview показывает точные ID, старые и новые пакеты и rollback; apply выполняется одной транзакцией и пишет audit event.

### SC-WPI-009 — браузер помнит архивный проект

**Дано:** local storage содержит project 15, проект 15 архивирован, project 10 активен.  
**Когда:** пользователь открывает publication tasks.  
**Тогда:** project 15 не загружается как рабочий; приложение выбирает project 10 или просит выбрать активный проект; старые задачи project 15 не показываются.

## 8. Исправление production-кода

Минимальный безопасный слайс:

1. Заменить `findFirst(project_id, orderBy id asc)` на точное разрешение периода.
2. Заполнять `plan_id`, `plan_version`, `timezone` у `WeekPackage`.
3. Не включать `week_package_id` в обычный update существующей cross-cycle задачи.
4. Добавить конфликт `CROSS_CYCLE_TASK_ID`.
5. Исправить server-side `active` и добавить фильтр недели.
6. Добавить e2e-тест двух последовательных delta-импортов.
7. Добавить repair-команду с dry-run для уже повреждённых проектов.
8. Валидировать сохранённый `currentProject` против активного списка и сбрасывать archived selection.

UI-исправление отдельным коммитом допустимо, но backend-инварианты должны быть готовы первыми.

## 9. Миграция и восстановление

Перед уникальным индексом:

1. Найти пакеты, охватывающие больше одного недельного диапазона задач.
2. Построить preview-группировку задач по `schedule_at` в timezone проекта.
3. Не переносить задачи без даты автоматически; вывести их в conflict report.
4. Не менять publication runtime.
5. Создать недостающие пакеты и связать задачи транзакционно.
6. Записать `WorkflowEvent` с before/after и обратной командой.

## 10. Безопасность и откат

- Repair доступен только owner/admin проекта.
- До apply обязателен dry-run с количеством и ID задач.
- Все изменения выполняются одной DB-транзакцией.
- При любом конфликте транзакция откатывается целиком.
- В логах нельзя выводить токены каналов, cookies и DSN базы.
- Rollback восстанавливает прежние `week_package_id` из audit before-state и удаляет только созданный repair-пакет, если на него не появились новые зависимости.

## 11. Наблюдаемость

События:

- `week_package.created`;
- `week_package.reused_exact_cycle`;
- `week_package.cross_cycle_reuse_blocked`;
- `publication_delta.imported`;
- `publication_delta.runtime_locked_skipped`;
- `publication_delta.cross_cycle_conflict`;
- `week_package.repair.previewed/applied/rolled_back`.

Алерты:

- один пакет содержит задачи более чем из двух календарных недель;
- пакет меняет `week_start/week_end` после привязки первой задачи;
- delta сообщает `previousPackagesUpdated > 0`;
- published task меняет `week_package_id`;
- active API возвращает published item.

## 12. UAT

Владелец проекта:

1. Открывает W10 и видит опубликованные задачи с текстом и permalink.
2. Открывает W11 и видит только задачи 17–23.08.
3. Импортирует одну новую задачу W11 и убеждается, что W10 не меняется.
4. Повторяет импорт и не получает дубль.
