# LOCK-025A engineering implementation

Owner-approved local scope only. Existing connect/callback HTTP surface now uses explicit current tenant-owned LinkedIn channel, non-demo Owner, exact expected identity and one-use durable state. Read-only status is displayed beside the existing-channel selector in Settings. No new channel is created by consent. Publication authority is unchanged.

Additive schema: `ProviderOAuthConnectionAttempt` / `planner.provider_oauth_connection_attempts`; unique opaque-state SHA256, browser-binding SHA256, initiating user/project/channel, provider/purpose, expected author URN or canonical personal profile slug, channel JSON canonical digest, fixed same-origin HTTPS frontend/API redirect/client, 10-minute expiry, pending/exchanging/completed/failed custody, timestamps/safe failure code. No raw state, auth code, cookie, token or provider body is persisted. Binding IDs intentionally remain immutable history even after related business record deletion; authorization always resolves current tenant-owned rows before use. No reset/drop/cleanup migration.

Exactly one pending→exchanging compare-and-set occurs before any provider exchange, inside a transaction rechecking current membership/channel. Final credential+completed+WorkflowEvent commit locks user, membership and channel in stable order; revocation, demo conversion or config change cannot race that commit. Network runs outside transactions. Unknown exchange/save remains consumed with fresh-consent guidance. A save failure never grants code replay.

A new credential is an AES-256-GCM envelope using existing channel encryption: token, actual verified metadata, project and channel are authenticated together. Editable outer config metadata must exactly match the sealed metadata and current tenant/channel before the generic API resolver returns verified=true. Legacy raw/encrypted token compatibility remains readable but unverified; it cannot create API readiness. Generic channel routes additionally protect server-owned fields. Existing sanitization recursively removes ciphertext and masks tokens. No bulk credential rewrite.

Provider protocol uses bounded fixed-destination no-redirect calls: token exchange, introspection (active/client/expiry/actual scope), Profile `/v2/me` with id/vanityName and action-specific exact organization authorization. Each request15seconds and64KiB response maximum; scope or provider-body secrets never enter logs. OpenID is not assumed. Post-read authorization requires both the actual account-specific read grant and one bounded Posts author-finder GET (count1, exact author, typed result). History is never adopted as a fact. Images read permission eligibility derives only from actual documented Images grants (rw_ads, w_organization_social, w_power_creators), with exact organization authority where applicable; it is explicitly not an actual image-read verification. Same-attempt Images GET must prove AVAILABLE and exact owner before any public Posts POST. Personal w_member_social alone and r_member_social alone never establish versioned Images GET permission. New API admission remains separate/default off.

Personal first binding requires an existing valid person URN, explicit Owner expected public URN, or canonical existing LinkedIn personal profile slug matching actual Profile API vanityName. Organization requires exact expected organization URN and actual ORGANIC_SHARE_CREATE approval. Account kinds cannot be silently switched.

Sources checked read-only during implementation: Microsoft Learn Token Introspection, Profile API, Organization Authorizations (2026-09). Deterministic protocol fixtures do not establish real app permission availability. Production grant/identity/readiness smoke and Owner UAT remain pending.

Current verification in progress; no production/provider calls or public export/deploy performed.

Initial approved browser cookie surface requires API_URL and FRONTEND_URL to have the same HTTPS origin. Cross-origin configuration fails with a specific configuration remedy; no global credentialed CORS expansion.

The restricted personal r_member_social request is disabled by default. An administrator may enable LINKEDIN_PERSONAL_READBACK_REQUEST_ENABLED only after application approval; actual introspection and the read probe must still pass. This flag creates no publication authority.
