# LinkedIn readback — proposed approval packet

Status: LOCK-LI-024 / QAR-LI-024 / ARCH-LI-024 / RISK-LI-024 approved by owner on 2026-10-19 for synthetic implementation. Original design below is retained; current implementation/results are in the package notes and combined TRUN. No live account, credentials or permission grant inspected.

## LOCK: outcome and operator boundary

For an authorized, immutable browser publication attempt whose result is uncertain, the existing Planner uncertainty/status surface must either record its uniquely verified LinkedIn object through the canonical publication-fact transaction, or explain the exact remaining block and repair action. It must never submit, grant a permit, create another attempt/key, or reinterpret absence as permission to resend.

Scope: a generic LinkedIn recovery reader and its application-owned admission/wiring. No task/account-specific authority. Existing accepted revision, approved manifest, author/account identity, exact body and media identity, tenant, approval and attempt history remain binding. Supported publication placements/content types must be declared individually; unsupported media/article/reshare types fail closed rather than falling back to text-only matching. Initially permit text-only and image posts only when media identity can be independently verified.

Actual capabilities: `linkedin.service.ts:250` contains `findRecentPublishedPosts`, a single latest-20 legacy `/v2/ugcPosts` lookup. It returns text/id/URL without publication time, asset verification, pagination, deadline or cancellation. `linkedin_task995_recovery.service.ts` is historical task-specific code and cannot become shared authority. Neither is an admitted general recovery reader. Search of `src` finds no application caller registering `createBrowserRecoveryOperation`; the deployed recovery foundation is not itself live readback.

Provider feasibility: official [Posts API documentation](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-07), checked 2026-10-19, describes replacement of ugcPosts, restricted `r_member_social` for personal reads, and `r_organization_social` plus company role for organization reads. Actual grants/roles and account transport are unverified. Write access is not evidence of read access. No personal account API promise can be made yet. A browser-routed account must remain blocked until an approved reader exists on that route; lack of API scope does not authorize browser/session injection or transport switching.

## ARCH: integration and admission

1. Add a small typed LinkedIn Posts read client; credentials resolved server-side from the tenant-owned approved channel binding. Version pin and response schema are explicit. Only allowlisted LinkedIn HTTPS API origins; pagination links must not become arbitrary fetch URLs. No redirects to untrusted hosts.
2. Application code admits a reader only for a supported account/route/placement with verified read permissions and identity. Platform-level `Map` registration alone cannot attest account permission. No RPC can supply a port, verification proof, credentials or admission flag. Capability discovery distinguishes implemented from admitted and reports safe permission/capability gaps.
3. Wire the existing `createBrowserRecoveryOperation` into the actual uncertainty boundary, using its durable repository, clock and canonical finalizer. Review the real MCP/API registration and serialization, not just unit-call the factory. Current runtime does not pass `knownObjectId`; introduce a durable, validated object-ID provenance source when the original attempt retained it. Never accept an arbitrary caller URL as provider proof.
4. Prefer GET of a known immutable object whose receipt was durably and trustworthily bound to the original attempt by the approved executor/provider boundary; verify author, published lifecycle, publication time and exact intended content/media. A caller-supplied URL or history-derived ID is not such a receipt. Otherwise enumerate the author's supported inventory with bounded pagination to collect candidate evidence only. Default sorting by modification time does not justify stopping when a creation timestamp falls below the lookup window. Continue to proven inventory exhaustion or return coverage incomplete. A latest-20 page alone never proves uniqueness/absence. Even complete inventory containing exactly one body/asset/time match cannot establish causal attribution to this attempt: an identical manual post is possible. History-only candidates remain UNKNOWN/held unless an independently reviewed provider/executor correlation mechanism proves their connection to the original attempt. Such a new mechanism requires its own evidence/approval review before admission; uniqueness alone never finalizes.
5. Match body against the exact frozen body hash using one documented deterministic provider serialization rule. Do not fuzzy-match, remove meaning-bearing whitespace or normalize away differences. Link previews, article identity, image hashes/provider media IDs and ordered attachment cardinality require explicit evidence. If API cannot prove accepted media bytes through a pre-recorded trusted upload/object binding, return incomplete coverage. Never copy expected hashes into evidence as if observed by the provider.
6. Keep raw responses/text in bounded process memory only. The verified evidence contains safe hashes, provider object identity, canonical public URL, published/observed times and evidence digest. Existing `coordinateBrowserRecovery` validates scope/hash/time and invokes guarded canonical finalization; it does not establish provider truth itself. Implement verification that proves provider origin and exact account before constructing this evidence. URL host must be `www.linkedin.com` or approved canonical LinkedIn host, with matching URN, no credentials/query/fragment, never merely an arbitrary HTTPS URL.
7. Fact/attempt/recovery/audit finalize atomically with approval/package/owner/permission/CAS rechecks and abort/deadline checks at commit. Existing `browser_recovery_guard.ts`, `browser_recovery_fact_transaction.ts` and `publication_fact.service.ts` remain canonical. Missing registration, revoked grants, malformed/partial inventory, multiple candidates or expired evidence preserve UNKNOWN.

## QAR: measurable limits and observability

- Preserve the existing durable maximum 3 rounds / 20 total provider requests / 180 seconds across calls and restarts; every page, exact-object GET, asset lookup and verification request consumes one durable token before network I/O. No hidden fetch retries outside that budget. Per-call timeout at most 30 seconds and remaining deadline; responses limited to 1 MiB and 100 parsed objects per page (proposed new hard limits).
- Zero send/upload/delete calls, new attempts, changed publication keys or permits during recovery; zero canonical success without independently validated evidence and an atomic guarded commit.
- Abort/shutdown stops new requests immediately; late responses cannot finalize. Retry transient 429/5xx/timeouts only within existing rounds/deadline, respecting Retry-After when it fits; oversized delay ends with an actionable held result. 401/403 is permission repair, never another transport.
- One structured allowlisted log at handling boundary per outcome, no token/header/cookie/body/provider payload/request arguments. Actual MCP/API result includes stable code, plain-language cause, concrete remedy and no-resend guidance. Bounded counts/timings suffice for recovered versus held metrics; no identifiers in metric labels.
- Synthetic acceptance must prove the real caller boundary and durable state, not only fake port success. Live admission remains disabled until owner-authorized bounded read-only smoke establishes actual route/account permissions; smoke makes zero publications. Synthetic success is not live readiness or owner UAT.

## RISK and rollback

Principal risks: same-body false positives; wrong author; truncated inventory; edit timestamps confused with publication; unverified image mapping; grants lost after admission; fabricated object ID; late callback; concurrent finalization/revocation; secret-bearing exceptions and pagination SSRF. Mitigations are exact original-package mapping, typed provider schemas/host checks, durable budgets, completeness flags, independent GET and atomic rechecks. Any unsupported proof remains UNKNOWN.

Disable new account/provider admission to stop new reads; retain recovery rows and writer holds even when `BROWSER_RECOVERY_V2_ENABLED` is false. Never downgrade a held v2 attempt into a legacy sender. Keep migrations additive and evidence/history intact. No automatic frozen-attempt backfill: historical attempts require an independently approved evidence-eligibility procedure; missing trustworthy v2 evidence remains legacy UNKNOWN.

## Proposed acceptance coverage and owner UAT (not final scenarios)

Coverage after approval: exact object with trusted attempt-bound receipt; caller-known URL rejected as correlation; complete paginated unique history match stays held without causal proof; identical manual post; duplicate body; wrong tenant/author/time/revision/asset; edited post; first-page-only/inventory truncation; unavailable scopes; company role loss; malformed/oversized response; invalid pagination URL; timeout/429/5xx; restart retains request budget; cancellation/late response; revocation/package mutation at commit; concurrent fact writer; actual MCP safe serialization; zero dispatch on every denied path. Quality gate, focused Docker acceptance tests and relevant build are required, with per-build TRUN. Existing debt must not be exempted or expanded.

Owner UAT after safe live admission: select an already-published approved object and read it without submitting; observe confirmed original attempt/fact and URL. Select a permission-denied/ambiguous case and see a precise repair instruction while UNKNOWN persists. No live publishing, activating readers, bulk historical reconciliation, migration or deploy is authorized by approving this design alone.

Approval requested: the above generic read-only API implementation with conditional per-route/account admission, bounded inventory proof, safe failure and canonical finalization. External scope grants, browser reader implementation and live admission remain separate prerequisites.
