# Safe preparation recovery — proposed approval packet

Status: LOCK-PREP-024 / QAR-PREP-024 / ARCH-PREP-024 / RISK-PREP-024 approved by owner on 2026-10-19 for synthetic implementation, including additive technical storage. Original design below is retained; protected ledger/outbox implementation and results are in package notes and combined TRUN. No live executor, provider operation or production mutation admitted.

## LOCK: useful behavior and unchanged publication authority

Recover a transient preparation failure automatically within the original approved publication attempt only when an admitted executor technically proves that no permit was ever issued, no dispatch occurred and the previous executor cannot act. Preserve accepted copy, revision, approval, manifest, account/media bindings, work item, attempt, key and audit history. Resume preparation, then require the normal first-permit checks; recovery itself never grants send permission. Any issued submit permit, uncertain dispatch, missing proof, changed package or denied permission holds the attempt for read-only reconciliation or specific repair. A preparation-only challenge that has never conveyed submit authority may be atomically superseded when its complete lifecycle proves zero live dispatch authority. A permit-phase challenge that conveys authority or whose non-consumption/supersession cannot be established remains blocking; merely calling a token a preparation challenge is insufficient.

User boundary: existing Planner publication/recovery status and authenticated owning executor pickup. No new operator requirement to paste technical proof or repeat unchanged business approval. Unsupported execution routes receive `PRE_DISPATCH_PROOF_UNAVAILABLE` plus concrete route-repair guidance. Dzen/VK remain documented Planner -> independent adapter only; no alternative sender/session/browser path. This initial proposal admits no Dzen/VK runtime or any browser executor until it implements the complete fence below.

## Evidence baseline: foundation exists; live executor does not

- `browser_recovery_resume.ts`: generic same-attempt CAS contract and application-owned `executorFence`; requires zero permits/dispatch, quiescence and supersession proof. Generates a private rotated lease and returns no send permission.
- `browser_recovery_resume_repository.ts`: serializable revalidation, historical permit/challenge checks, generation increment, work lease rotation, X phase supersession and audit; factory with no fence remains unsupported.
- `browser_publication_execution.ts`: normal start/pre-submit/uncertainty lifecycle; start creates an attempt but not a pre-permit v2 preparation record. Pre-submit rejects attempts with `error_message`. Therefore merely registering a fence cannot make resumed attempts runnable while preserving error history.
- `browser_recovery_runtime.ts`: current recovery admission creates RECONCILING/UNKNOWN rows after uncertainty; not a preparation proof producer.
- `browser_recovery_guard.ts` and `browser_publication_guard.ts`: any persisted v2 row holds legacy writers. The only admitted bypass is canonical finalization; there is no generation-scoped pre-permit pickup/permit capability.
- Source-wide search finds no application registration of an executorFence, no actual resume invocation/pickup consumer. Existing synthetic resume tests prove only contracts, not operational recovery.

## ARCH: minimal complete shared mechanism

1. Add an application-owned durable execution reservation for a supported executor, bound to tenant/work/attempt, immutable package and executor generation. Create PREPARE/NOT_DISPATCHED recovery state atomically at original start only when the registered executor owns the exclusive dispatch boundary. Never infer non-delivery from timeout, expired lease, missing result or lack of a DB permit event alone. Older attempts lacking proof stay held.
2. Every entry point that can issue a challenge/permit, start dispatch, accept a result, rotate a lease, advance a native phase or create a canonical fact must consult the same execution generation and hold. Inventory generic and historical specialized writers by call graph before implementation. Historical task-specific routes cannot inherit new authority; block them on the v2 hold unless separately migrated generically. New account/task IDs are validated data, never new allowlists/exports.
3. Quiesce the previous executor at its authoritative supervisor/adapter boundary: revoke its reservation, stop in-flight preparation, await a terminal cancellation acknowledgement, and invalidate all prior challenges/nonces. The supervisor supplies durable evidence tied to exact generation/attempt, not a caller boolean or process-local map. If it cannot guarantee the previous generation cannot click/send (including an already-loaded browser), it must return unsupported proof. Lease expiry alone is insufficient. Process restart must recover a durable tombstone; offline old workers remain unable to dispatch when they return.
4. In a serializable transaction, recheck owner/role, active approval, frozen package, one original attempt, zero issued submit permits, zero live challenge/dispatch authority and executor proof. Preparation-only unconsumed challenges may be superseded in the same transaction when all readers reject the old generation; issued permits cannot be superseded into new send authority. Atomically CAS row/generation, rotate private lease, supersede safe challenge families, append audit and enqueue one generation-bound pickup. An outbox or equivalent durable claim must avoid commit-without-pickup loss. Redelivery is idempotent and cannot allocate another attempt or generation.
5. Expose only an authenticated internal pickup to the registered executor. Return no lease/token to general status callers or logs. Executor verifies generation and lease with Planner before each step. Introduce a narrowly scoped internal preparation/first-permit capability integrated with the existing hold; do not globally suppress `assertBrowserRecoveryWriter`, clear `error_message`, reset attempt status or reuse finalization bypass. Keep original error in history. Atomically mark first permit issuance and consume nonce; all later recovery is reconciliation-only even if permit expires or a click was not observed.
6. Bounded retries apply only to classified transient preparation failures before dispatch: e.g. isolated network retrieval or worker restart with proven quiescence. Wrong account, rejected art/review, denial, package mismatch, missing capability and malformed data are not transient. Do not automatically renew business approval or reinterpret session/approval rejection as permission.
7. Keep recovery stage advancement, accepted results and canonical facts protected by generation/row-version CAS and existing transactional finalizer. On stale callback return a stable conflict without mutation. Read-only status reports what remains and system's next action; technical recovery does not produce a fake success fact.

## QAR: measurable boundaries

- Proposed preparation budget: at most 3 automatic resumptions and 180 seconds total from first recovery eligibility, durable across restart/replay, with attempts at offsets 0/30/120 seconds when remaining time permits. No budget reset by new caller/key. This is separate from the already approved readback budget and must be reported separately. A 900-second rotated lease lifetime in the existing helper is an ownership ceiling, not permission to extend the 180-second recovery budget; it must be clipped to the remaining preparation deadline.
- Supervisor quiescence acknowledgement must arrive within 10 seconds and the remaining deadline; otherwise hold and do not rotate authority. Database transaction timeout remains at most 10 seconds. No synchronous process kill/wait inside an unbounded DB transaction; obtain candidate evidence first and revalidate generation/tombstone transactionally.
- Zero duplicate attempts, send keys or active generation owners. Zero first-permit issuance to stale generation. Zero preparation resumption after any submit-permit/dispatch uncertainty or unproven challenge authority. Supersession of a proven preparation-only challenge must leave zero usable old-generation authority. Race tests must prove stale executors cannot reach the mocked dispatch boundary, not merely that a status row changed.
- One actionable safe serialized result for success/held/exhausted/permission/package/conflict; no raw exceptions, cookies/tokens/headers/approval references/body/provider payload in responses or logs. Metrics: bounded enum cause, resumptions, exhausted/held counts and latency; no task/account metric labels.
- All acceptance, persistence/race tests, quality gate and relevant builds run only in Docker against synthetic isolated state. Capture per-build TRUN. GREEN remains owner UAT pending; actual provider execution is a separate admission gate.

## RISK, compatibility and rollback

Highest risk is a zombie executor acting after technical state says NOT_DISPATCHED. Fencing only in Planner is insufficient if an old browser can submit independently; that route remains unsupported until the executor itself is fenced. Another risk is changing error handling to silently allow any failed attempt; use typed generation-scoped capability instead of clearing error or weakening guards. Scope collisions, callback races, duplicate outbox delivery and crash-between-rotation/pickup require durable uniqueness/CAS.

Production admission starts disabled per supported executor, not globally for all providers. Additive schema fields/outbox (if required) get a restore-tested migration and explicit rollout approval. Rollback stops new resumptions and pickup but retains tombstones, generations, evidence and v2 writer holds. Never reactivate a prior generation or downgrade UNKNOWN. In-flight first-permit attempts remain reconcile-only. No existing frozen attempt is automatically enrolled.

## Proposed acceptance coverage / operator UAT (before final scenario authoring)

Coverage: proven no-permit transient recovery with same attempt; unsupported fence; lost quiescence ACK; live zombie worker and stale queued callback; restart before/after CAS/pickup; two concurrent recoverers; generation/replay mismatch; stale/issued challenge; permit issued but response lost; revoked approval/changed package; wrong role/tenant/account; outbox redelivery; stale writer/fact callback; crash recovery preserving error/audit; budget exhaustion; cancellation; real MCP/API serialization and no secret leakage. Inventory every mutable path first, including generic start/permit/claim/uncertainty/confirm, native phase/challenge and canonical fact, then require a preservation test for each relevant writer.

Owner UAT after engineering checks: inject a synthetic preparation timeout and observe automatic same-attempt continuation with no renewed approval. Inject an unsupported fence or a lost permit response and observe a precise held/reconciliation explanation, with no second submission. A live route is admitted only after its supervisor implementation and bounded smoke are verified separately.

Approval requested: shared durable executor ownership/generation, pre-permit record creation, technical quiescence and bounded same-attempt preparation pickup/first-permit integration, preserving all old error/authority/history. This approval alone does not activate publishers/consumers, apply a production migration, deploy, or resume old attempts.
