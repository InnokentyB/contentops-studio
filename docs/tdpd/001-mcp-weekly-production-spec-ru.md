# TDPD-001: MCP-очередь недельного контент-производства

Статус: draft for product approval  
Режим: TDPD Plan  
Метод: Test-Driven Product Development (TDPD), оригинальный метод Иннокентия Бодрова  
Версия: 0.1  
Дата: 2026-08-09

## 1. Назначение документа

Документ определяет первый вертикальный слайс новой концепции BA Post Planner: управляемый через MCP двухпроходный цикл подготовки недельного контента с расписанием, агентным одобрением и детерминированным учётом просрочки.

В этот слайс не входит полноценная реализация автопостинга, генерации изображений и аналитики кампаний. Однако модель процесса должна позволить добавить их следующими слайсами без второго параллельного workflow.

TDPD-цепочка этого слайса:

`бизнес-проблема → требования → пользовательские сценарии → e2e-тесты → реализация → приёмка (UAT)`

## 2. Бизнес-проблема

### BP-001

Владелец контентного процесса работает через внешних агентов, например Claude Cowork и Codex. Один агент первым проходом формирует недельный план: общий фрейм, темы, источники, каналы и расписание. Другой агент вторым проходом дописывает материалы.

Сейчас планнер хранит материалы и публикационные статусы, но не даёт агентам единого детерминированного рабочего контракта: какое задание можно взять следующим, какой результат требуется, какое одобрение блокирует продолжение и какой именно этап просрочен.

Из-за этого владелец процесса вынужден вручную переносить контекст между агентами и самостоятельно восстанавливать состояние расписания.

### Акторы

- **Владелец процесса** — определяет архитектуру и правила, разбирает исключения, проводит приёмку (UAT).
- **Агент-планировщик** — создаёт или обновляет недельный пакет через MCP.
- **Агент-автор** — получает через MCP задание второго прохода и возвращает готовый текст.
- **Агент-ревьюер** — одобряет или отклоняет результат, если это требует политика этапа.
- **Планнер** — хранит артефакты и workflow, рассчитывает доступность и просрочку, обеспечивает идемпотентность и изоляцию проектов.
- **Планировщик времени** — инициирует проверки сроков; может быть фоновым процессом, но результат обязан быть наблюдаем через MCP.

### Желаемый результат

Агент может через MCP без ручной передачи контекста:

1. создать недельный план;
2. получить следующее доступное задание;
3. безопасно закрепить задание на время выполнения;
4. вернуть результат или зафиксировать блокировку;
5. запросить и получить одобрение;
6. увидеть просроченные этапы и причину каждого исключения.

### Сигналы успеха

- Для 100% активных материалов система может назвать одно текущее следующее действие или явную причину ожидания.
- Для 100% просроченных материалов система возвращает конкретный просроченный этап и дедлайн, а не общий статус `overdue`.
- Повторный MCP-вызов с тем же ключом идемпотентности не создаёт дублей и не повторяет переход состояния.
- Агент второго прохода получает весь обязательный контекст одним MCP-чтением либо явный список недоступных ресурсов.
- В UAT владелец может понять состояние недели и проблемные материалы без чтения логов и базы данных.

## 3. Границы первого слайса

### Входит

- импорт или создание недельного плана через MCP;
- декомпозиция каждого материала на исполнимые этапы;
- очередь доступных работ для агентов;
- claim/lease-механизм для защиты от параллельного выполнения;
- завершение, блокировка и повтор этапа;
- агентное одобрение результата второго прохода;
- отдельные дедлайны подготовки и публикации;
- вычисляемое состояние расписания;
- MCP-чтение исключений и просрочек;
- история переходов и решений;
- изоляция проектов и проверка полномочий MCP-актора.

### Не входит

- фактическая публикация в социальные сети;
- генерация или выбор изображений;
- сбор фактических метрик;
- автоматическая генерация подтем для каналов;
- сложные правила кампаний;
- редизайн всех существующих экранов;
- оценка качества текста моделью.

### Связанные последующие слайсы

- **Сквозное планирование релиза:** универсальные инициативы четырёх слоёв, граф зависимостей, release readiness и аудит покрытия. Зафиксировано в `case-cross-layer-release-planning-ru.md` и должно быть специфицировано до расширения календаря и кампанийной аналитики.
- **TDPD-002 Автопостинг:** тема кампании → подтемы каналов → агентное одобрение → контент → публикация.
- **TDPD-003 Визуальный pipeline:** визуальный бриф → версия промпта → варианты → одобрение → выбранный asset.
- **TDPD-004 Метрики и кампании:** точки замера → сбор → нормализация → агрегация → выводы для следующего плана.
- **TDPD-005 Замещение ручного постинга:** поэтапное переключение одного материала между manual handoff, публикацией агентом и прямым адаптером.

## 4. Архитектурная граница для одобрения человеком

### ADR-001: материал отделён от исполнимой работы

- `ContentItem` — контентный артефакт: тема, источники, текст, канал и связь с недельным пакетом.
- `WorkItem` — отдельный исполнимый этап, связанный с `ContentItem` или недельным пакетом.
- `ApprovalDecision` — неизменяемое решение по версии результата.
- `WorkflowEvent` — журнал значимых переходов и MCP-действий.

Не использовать единое поле `ContentItem.status` как источник истины одновременно для производства, одобрения, публикации и просрочки.

### ADR-002: состояние срока вычисляется

`schedule_health` не хранится как ручной статус. Оно вычисляется из текущего этапа, дедлайна, блокировок и текущего времени.

Допустимые значения первого слайса:

- `unscheduled` — у текущего обязательного этапа нет дедлайна;
- `on_track` — дедлайн не наступил;
- `due_soon` — дедлайн наступит внутри настраиваемого окна;
- `overdue` — дедлайн прошёл, этап не завершён;
- `complete` — обязательные этапы слайса завершены.

`blocked` относится к состоянию выполнения, а не к состоянию расписания. Поэтому задание может одновременно иметь `state: blocked` и `schedule_health: overdue`.

### ADR-003: агенты работают через lease

Claim выдаёт агенту ограниченную по времени аренду задания. Завершить или заблокировать этап можно только с действующим `lease_token`. Истёкшая аренда возвращает незавершённое задание в очередь и сохраняется в истории.

### ADR-004: существующий publication plan остаётся входным контрактом

Первый слайс расширяет существующий импорт `publication-plan.json`, а не создаёт второй формат недельного плана. Нормализатор должен получить обязательные для workflow поля и создавать или обновлять `ContentItem` и связанные `WorkItem`.

Из-за контейнерной изоляции источники не должны зависеть от локальных путей хоста. Для ресурсов используются inline snapshots или HTTP/HTTPS URL. Недоступный источник возвращается как наблюдаемая ошибка контекста.

### ADR-005: публикация остаётся отдельной политикой исполнения

Будущие режимы `manual_handoff`, `agent_via_mcp` и `direct_adapter` не меняют контентный артефакт и его кампанию. Первый слайс только сохраняет будущую точку расширения `publication_mode`; публикационный адаптер не вызывается.

## 5. Модель и термины

### 5.1. WeekPackage

Недельный контекст:

- период и timezone;
- общий фрейм и тезис;
- цели и источники;
- версия плана;
- состояние одобрения плана.

### 5.2. ContentItem

Материал недели:

- стабильный внешний `item_key` внутри плана;
- тема и назначение;
- канал и формат;
- ссылки или snapshots источников;
- дедлайн готовности `content_due_at`;
- плановый слот `publish_at`;
- текущая версия текста;
- будущие `review_policy` и `publication_mode`.

### 5.3. WorkItem

Исполнимая единица работы:

- `kind`: `plan_review`, `content_write`, `content_review`;
- `state`: `pending`, `available`, `claimed`, `waiting_approval`, `blocked`, `completed`, `cancelled`;
- роль исполнителя;
- обязательные зависимости;
- дедлайн этапа;
- версия входного контекста;
- версия результата;
- lease и история попыток.

### 5.4. ApprovalDecision

- относится к конкретной версии результата;
- решение: `approved` или `rejected`;
- actor и timestamp;
- комментарий обязателен при `rejected`;
- повтор того же решения с тем же idempotency key безопасен;
- новое решение не переписывает историю предыдущего.

## 6. Детерминированные требования

### План и создание работы

- **R-001.** Принятый недельный план обязан иметь project, timezone, границы недели, общий фрейм и хотя бы один материал.
- **R-001a.** Успешный импорт возвращает стабильные `project.id` и `week_package.id`, необходимые для последующих MCP-команд.
- **R-002.** Каждый материал обязан иметь стабильный `item_key`, тему, канал или явное `channel_pending`, `content_due_at` и `publish_at`.
- **R-003.** `content_due_at` должен быть не позже `publish_at`.
- **R-004.** Повторный импорт той же версии плана не создаёт дублей.
- **R-005.** Delta-обновление не переписывает завершённый результат или опубликованный материал без отдельной команды пересмотра.
- **R-006.** После одобрения недельного плана система делает `content_write` доступным только при наличии обязательных источников.

### Очередь и выполнение

- **R-007.** MCP-очередь по умолчанию возвращает только доступные задания проекта, отсортированные: `overdue` → ближайший дедлайн → приоритет → стабильный ID.
- **R-008.** Задание с незавершённой зависимостью не возвращается как доступное.
- **R-009.** Успешный claim атомарно переводит задание в `claimed` и возвращает `lease_token` и `lease_expires_at`.
- **R-010.** Одновременно действителен не более одного lease на задание.
- **R-011.** Повтор claim с тем же idempotency key возвращает исходный успешный результат.
- **R-012.** Другой агент не может завершить задание без действующего lease token.
- **R-013.** Истёкший lease возвращает задание в доступную очередь; предыдущая попытка остаётся в истории.
- **R-014.** Агент может завершить этап, зарегистрировать блокировку или освободить lease без результата.
- **R-015.** Завершение `content_write` создаёт новую неизменяемую версию текста и переводит связанный review в доступное состояние.

### Одобрение

- **R-016.** Одобрение применяется только к конкретной актуальной версии результата.
- **R-017.** Одобрение устаревшей версии отклоняется без изменения состояния.
- **R-018.** `approved` завершает `content_review` и делает материал готовым для следующего будущего этапа.
- **R-019.** `rejected` требует комментарий, создаёт новую попытку `content_write` с этим комментарием и не уничтожает предыдущую версию.

### Время, просрочка и блокировки

- **R-020.** Все timestamps хранятся как UTC instants; план сохраняет IANA timezone для отображения и расчёта локальных слотов.
- **R-021.** Этап становится `overdue`, когда `now > due_at` и этап не `completed`/`cancelled`.
- **R-022.** Ровно в `due_at` этап ещё не считается просроченным; просрочка начинается после дедлайна.
- **R-023.** Для каждого исключения MCP возвращает `reason_code`, дедлайн, длительность просрочки и рекомендуемое следующее действие.
- **R-024.** Если подготовка контента просрочена, но `publish_at` ещё не наступил, причина — `content_overdue`, а не `publication_missed`.
- **R-025.** Если `publish_at` прошёл и материал не опубликован, будущий публикационный этап должен возвращать `publication_missed`; первый слайс отображает этот риск, но не публикует материал.
- **R-026.** `blocked` не отменяет течение дедлайна. Заблокированное задание после дедлайна остаётся blocked и дополнительно имеет `is_overdue: true`.
- **R-027.** Перенос дедлайна требует причины и создаёт событие; история прежнего дедлайна сохраняется.

### Безопасность и наблюдаемость

- **R-028.** MCP-актор может читать и изменять только проекты, к которым имеет доступ.
- **R-029.** Ответы MCP не возвращают секреты каналов и провайдеров.
- **R-030.** Все изменяющие MCP-команды требуют `actor_id` и `idempotency_key`.
- **R-031.** Каждое изменение состояния создаёт событие с actor, command, before/after state, correlation id и timestamp без сохранения секретов.
- **R-032.** Невалидный переход возвращает машинно-читаемый `error_code` и не создаёт частичного изменения.

## 7. Предлагаемый MCP-контракт первого слайса

Названия предварительные, но внешнее поведение является частью спеки.

### Чтение

- `ba_list_work_items(projectId, actorId, filter?, asOf?)`
- `ba_get_work_item(projectId, actorId, workItemId)`
- `ba_get_work_item_context(projectId, actorId, workItemId, maxChars?)`
- `ba_list_schedule_exceptions(projectId, actorId, asOf?, includeBlocked?)`
- `ba_get_week_execution_summary(projectId, actorId, weekPackageId, asOf?)`

`asOf` существует для детерминированных тестов времени. В production при отсутствии используется текущее серверное время.

### Изменение состояния

- `ba_decide_week_plan(projectId, actorId, weekPackageId, planVersion, decision, comment?, idempotencyKey)`
- `ba_claim_work_item(projectId, actorId, workItemId, leaseSeconds?, idempotencyKey)`
- `ba_complete_work_item(projectId, actorId, workItemId, leaseToken, result, idempotencyKey)`
- `ba_block_work_item(projectId, actorId, workItemId, leaseToken, reasonCode, note?, idempotencyKey)`
- `ba_release_work_item(projectId, actorId, workItemId, leaseToken, idempotencyKey)`
- `ba_decide_approval(projectId, actorId, workItemId, resultVersion, decision, comment?, idempotencyKey)`
- `ba_reschedule_work_item(projectId, actorId, workItemId, dueAt, reason, idempotencyKey)`

### Минимальная форма ответа очереди

Каждый элемент возвращает:

- идентификаторы project/week/content/work item;
- `kind`, `state`, `assignee_role`;
- `due_at`, `schedule_health`, `is_overdue`, `overdue_seconds`;
- краткое описание ожидаемого результата;
- зависимости и блокировки;
- `next_action`;
- версию контекста;
- ссылку на MCP-команду получения полного контекста.

## 8. Пользовательские сценарии

### SC-001 — Планировщик создаёт недельную очередь

**Начальное состояние:** у проекта нет пакета на заданную неделю; MCP-актор имеет доступ к проекту.  
**Действие:** агент-планировщик импортирует валидный недельный план и затем одобряет его.  
**Наблюдаемый результат:** создан один WeekPackage, материалы без дублей и доступные `content_write` для материалов с полным контекстом.  
**Побочные эффекты:** создана история импорта и одобрения; сохранена timezone.  
**Критерий:** сводка недели показывает ожидаемое число материалов и однозначное следующее действие для каждого.

### SC-002 — Автор получает ближайшую просроченную работу первой

**Начальное состояние:** доступны три задания: одно просрочено, два имеют будущие дедлайны.  
**Действие:** агент запрашивает очередь доступной работы.  
**Наблюдаемый результат:** просроченное задание возвращается первым с причиной `content_overdue`, величиной просрочки и следующим действием `claim`.  
**Критерий:** порядок не зависит от порядка создания записей.

### SC-003 — Автор безопасно забирает и завершает второй проход

**Начальное состояние:** `content_write` доступен и содержит разрешимые источники.  
**Действие:** агент делает claim, получает контекст и завершает работу с готовым текстом.  
**Наблюдаемый результат:** создана новая версия текста; `content_write` завершён; `content_review` доступен.  
**Побочные эффекты:** lease закрыт, переходы записаны в историю.  
**Критерий:** повтор completion с тем же idempotency key не создаёт вторую версию.

### SC-004 — Два агента одновременно пытаются взять одно задание

**Начальное состояние:** одно задание доступно.  
**Действие:** два разных агента почти одновременно выполняют claim.  
**Наблюдаемый результат:** только один получает действующий lease; второй получает `WORK_ITEM_ALREADY_CLAIMED`.  
**Критерий:** в хранилище существует ровно один активный lease.

### SC-005 — Истёкший lease восстанавливает очередь

**Начальное состояние:** агент получил lease и не завершил работу до его истечения.  
**Действие:** другой агент запрашивает очередь после `lease_expires_at`.  
**Наблюдаемый результат:** задание снова доступно, предыдущая попытка помечена истёкшей.  
**Критерий:** старый token больше не может завершить задание.

### SC-006 — Ревьюер одобряет актуальную версию

**Начальное состояние:** текст версии N ожидает одобрения.  
**Действие:** агент-ревьюер одобряет версию N.  
**Наблюдаемый результат:** review завершён; материал отражается как готовый к следующему этапу.  
**Критерий:** решение связано именно с версией N и отображается в истории.

### SC-007 — Ревьюер отклоняет текст с комментарием

**Начальное состояние:** текст версии N ожидает одобрения.  
**Действие:** ревьюер отклоняет версию с непустым комментарием.  
**Наблюдаемый результат:** создаётся новая доступная попытка `content_write`; контекст содержит комментарий; версия N сохраняется.  
**Критерий:** новый автор видит причину отклонения одним вызовом получения контекста.

### SC-008 — Одобрение устаревшей версии отклоняется

**Начальное состояние:** после версии N уже создана версия N+1.  
**Действие:** ревьюер пытается одобрить N.  
**Наблюдаемый результат:** MCP возвращает `STALE_RESULT_VERSION`; актуальное состояние не меняется.  
**Критерий:** ни одна версия не получает ошибочного одобрения.

### SC-009 — Неполный источник блокирует написание

**Начальное состояние:** материал ссылается на локальный путь хоста, недоступный контейнеру, и не имеет snapshot/URL.  
**Действие:** план одобряется или агент запрашивает контекст.  
**Наблюдаемый результат:** `content_write` не выдаётся как доступный; исключение содержит `SOURCE_UNAVAILABLE` и список refs.  
**Критерий:** запрос не зависает и не возвращает пустой контекст как успешный.

### SC-010 — Система различает просрочку текста и пропущенную публикацию

**Начальное состояние:** `content_due_at` прошёл, `publish_at` ещё впереди, текст не готов.  
**Действие:** агент запрашивает исключения.  
**Наблюдаемый результат:** причина `content_overdue`, не `publication_missed`. После наступления `publish_at` добавляется риск пропущенной публикации.  
**Критерий:** обе контрольные точки имеют собственные timestamps и причины.

### SC-011 — Заблокированное задание продолжает стареть

**Начальное состояние:** агент заблокировал работу до дедлайна.  
**Действие:** исключения запрашиваются после дедлайна.  
**Наблюдаемый результат:** состояние остаётся `blocked`, а `is_overdue` становится true; ответ содержит исходную блокировку и величину просрочки.  
**Критерий:** блокировка не скрывает нарушение расписания.

### SC-012 — Перенос дедлайна сохраняет аудит

**Начальное состояние:** работа просрочена.  
**Действие:** уполномоченный актор переносит дедлайн с причиной.  
**Наблюдаемый результат:** новый срок влияет на очередь; предыдущий срок и причина переноса доступны в истории.  
**Критерий:** перенос без причины отклоняется.

### SC-013 — Повторный импорт не повреждает выполняемую работу

**Начальное состояние:** недельный план импортирован, один текст завершён, другой claimed.  
**Действие:** агент повторяет тот же импорт или присылает delta с новой темой.  
**Наблюдаемый результат:** завершённая версия и активный lease сохраняются; новый материал добавляется; дублей нет.  
**Критерий:** результат соответствует delta-safe семантике.

### SC-014 — Актор другого проекта не видит и не меняет работу

**Начальное состояние:** actor имеет доступ к проекту A, work item принадлежит проекту B.  
**Действие:** actor читает, claim-ит или завершает work item B.  
**Наблюдаемый результат:** операция отклонена без раскрытия контекста или существования защищённого объекта.  
**Критерий:** состояние и журнал проекта B не меняются.

### SC-015 — Пустая очередь объяснима

**Начальное состояние:** доступных заданий нет, но есть ожидающие зависимости или одобрения.  
**Действие:** агент запрашивает очередь и недельную сводку.  
**Наблюдаемый результат:** очередь пуста; сводка объясняет числа `waiting_dependency`, `waiting_approval`, `complete`.  
**Критерий:** агент отличает «вся работа закончена» от «работа заблокирована».

## 10. Приоритет первого red-green-refactor цикла

### Red Gate A — минимальный полезный агентный цикл

Сначала реализуются падающие E2E-001, E2E-002, E2E-003, E2E-006, E2E-009, E2E-010 и E2E-014.

Они доказывают:

- план превращается в работу;
- агент получает правильное следующее действие и контекст;
- результат проходит одобрение;
- сроки объяснимы;
- проекты изолированы.

### Red Gate B — надёжность агентных повторов

Затем E2E-004, E2E-005, E2E-007, E2E-008 и E2E-013.

Они закрывают конкуренцию, истечение lease, повторную работу, stale decisions и повторные импорты.

### После первого green

E2E-011, E2E-012 и E2E-015 добавляют операционную прозрачность, но не должны задерживать проверку основного цикла, если архитектура уже сохраняет необходимые данные.

## 11. Критические углы и отказы

- два агента claim-ят одно задание;
- агент повторяет completion после сетевого timeout;
- lease истекает одновременно с completion;
- план повторно импортируется во время активной работы;
- источник указан локальным путём, недоступным Docker-контейнеру;
- DST меняет локальное смещение внутри недели;
- дедлайн текста равен времени публикации;
- rejected-версия уже не актуальна;
- blocked-задание пересекает дедлайн;
- актор подставляет projectId чужого проекта;
- частичная ошибка между сохранением результата и событием аудита;
- очень большой source snapshot превышает MCP response limit.

## 12. Ручная приёмка (UAT)

Автоматические тесты не доказывают удобство реальной работы с Claude Cowork или Codex. Владелец выполняет следующий сценарий:

1. Даёт агенту-планировщику реальный недельный фрейм и просит создать план через MCP.
2. В новом агентном сеансе просит получить следующую работу без копирования контекста вручную.
3. Агент читает источники, возвращает текст и отправляет его на одобрение.
4. Агент-ревьюер отклоняет одну версию и одобряет исправленную.
5. Владелец переводит тестовое время после одного дедлайна и просит агента объяснить состояние недели.
6. Владелец оценивает, можно ли принять решение о следующем действии без базы, логов и ручной сверки календаря.

### UAT-критерии

- контекст не приходится вручную переносить между агентами;
- очередь выдаёт ожидаемую работу;
- причина просрочки понятна без технической диагностики;
- одобрение и отклонение не теряют версии;
- состояние недели соответствует ментальной модели владельца;
- MCP-команды достаточно ясны, чтобы агент выбрал их без специальной подсказки на каждый шаг.

## 13. Тестируемость и открытые решения

### Достаточно определено для написания первых red-тестов

- разделение артефакта, исполнимого этапа и одобрения;
- отдельные `content_due_at` и `publish_at`;
- вычисляемая просрочка;
- MCP-first интерфейс;
- идемпотентность и lease;
- container-safe источники;
- delta-safe повторный импорт.

### OQ-001 — Момент одобрения недельного плана

Кто и каким MCP-действием одобряет план: тот же агент-планировщик, отдельный агент-ревьюер или владелец? Рекомендация для первого слайса: отдельная роль `plan_reviewer`, которой может управлять внешний агент.

### OQ-002 — Окно `due_soon`

Нужно определить значение по умолчанию и возможность настройки. Рекомендация: 24 часа на уровне проекта.

### OQ-003 — Длительность lease

Рекомендация: 30 минут по умолчанию с явным продлением в последующем слайсе. В первой версии можно разрешить `leaseSeconds` в безопасном диапазоне 60–3600.

### OQ-004 — Обязательность канала в первом проходе

Рекомендация: разрешить `channel_pending`, но такой материал остаётся blocked до назначения канала.

### OQ-005 — Кто имеет право переносить дедлайн

Рекомендация: только владелец или роль `scheduler`; обычный автор может лишь зарегистрировать блокировку.

### OQ-006 — Граница первого UI

Рекомендация: MCP является обязательным интерфейсом слайса; UI ограничивается сводкой недели и списком исключений после стабилизации MCP-контракта.

### OQ-007 — Связь с кампаниями

Рекомендация: добавить nullable `campaign_id` в контракт сразу, но не реализовывать кампанийные правила до TDPD-004.

## 15. Статус TDPD-гейтов

- **Input gate: открыт для Red Gate A.** Владелец запросил переход от спеки к тестам. Для первого цикла используются рекомендованные решения ADR-001–ADR-005 и OQ-001–OQ-007; они остаются изменяемыми до начала production-реализации.
- **Red gate: подтверждён для Red Gate A.** Семь исполняемых MCP e2e-тестов реализованы в `tests/tdpd/work-queue-mcp.e2e.test.js`. Команда `npm run test:tdpd:red` запускает реальный MCP server; 2026-08-09 все 7 тестов упали по ожидаемой причине — workflow-команды из этой спеки ещё не зарегистрированы. Инфраструктурный MCP smoke и backend build проходят.
- **Green gate: не начат.** Production-код не менялся.
- **Output gate: не начат.** Приёмка (UAT) возможна только после зелёных e2e-тестов и реализации.

Для выполнения DB-backed частей тестов после регистрации MCP-команд требуется отдельная тестовая база и переменные `TDPD_TEST_DATABASE_URL`, `TDPD_TEST_USER_ID`; для проверки межпроектной изоляции также `TDPD_TEST_OTHER_USER_ID`. Тесты намеренно не используют неявный `DATABASE_URL`, чтобы не создавать fixtures во внешней или production-базе.

## 16. Следующее решение владельца

После одобрения этой спеки следующий TDPD-шаг — реализовать минимальную MCP e2e-инфраструктуру и Red Gate A до любых production-изменений.
