# Historical manual publication confirmation

Status: DESIGN READY — awaiting human LOCK/QAR/ARCH/RISK approval before scenarios/RED. TDPD026. Source inspected: production5b5bb0324d8f6b7003c0ca1fa2ca2e681c451c4b/tree355fdc17bcbdd04a617ae8b45845c6298b46fc12. No implementation, provider access, fact writes or deploy performed by this design.

## Problem, surface and LOCK026

An owner has already published an external object and confirmed its permalink and publication time. Planner still shows a delivery debt because generic fact recording correctly refuses changes to an aggregate with owned/legacy publication history. Existing reconciliation requires an actual attempt or connector custody and supported provider evidence. Historical manual accounting is a distinct authority; it must not fabricate an attempt or pretend that an old UNKNOWN delivery succeeded.

Canonical truth remains PublicationFact. Add a common Owner-only Planner MCP preview/commit interface for a manually confirmed existing VK post or Dzen article, using shared provider permalink identity validators. Other formats/providers fail explicitly as unsupported until their identity contract is implemented. No production business-ID branches or exact task commands. No new UI screen: existing task/fact readbacks present manual provenance and whether a published revision is known. Proposed interface names: ba_preview_owner_manual_publication_confirmation, ba_confirm_owner_manual_publication. They do not yet exist.

Success: a permitted Owner can account for an existing object once, see its fact ID, declared time basis and publication-origin evidence, while previous delivery custody remains unchanged and no provider operation occurs. A blocked/UNKNOWN prior delivery is still visibly unresolved. Published fact is evidence that the owner confirmed an external object, not evidence of an automatic send, provider timestamp or current revision acceptance.

### Data and deterministic behavior

- Authenticate real principal from server context: profile owner, actor exactly its user identity, current non-demo user and owner membership for the tenant. Lock user/membership through commit. A caller-supplied actor/reference/URL never establishes ownership by itself. Writer/planner/publisher/editor/research profiles cannot invoke the mutating surface even if backed by the same user ID.
- Preview is read-only, no audit writes, provider/network calls or secret reads. Return a bounded versioned envelope: project/task/channel, current manifest checksum, exact task/fact/transport snapshot digests, normalized external-object identity, safe blockers, manual-origin semantics, and the fields commit must echo. No content bodies, session values, tokens or private provider payloads in the envelope.
- Require Owner attestation tying the external object to the tenant-owned task/channel, an explicit confirmation reference, publication time and basis. Initial supported basis OWNER_CONFIRMED_MESSAGE_TIME: preserve the original offset-bearing ISO timestamp including supplied microseconds in the audit; disclose millisecond precision in canonical Date persistence. Reject ambiguous local time, malformed/future time and missing evidence. Native provider time is not a prerequisite and is never invented. Server attests authenticated Owner assertion, not authenticity of arbitrary pasted chat text.
- Owner-supplied publication revision is optional. If supplied it must bind an actual retained immutable revision/body digest; otherwise published_revision=null / revision_binding=external_object_only. Current revision, accepted revision, text/visual approvals and selected asset do not change. A current unaccepted edit must never be labelled accepted or proven to be the external object's body.
- Permalink normalization is local and strict. Accept canonical supported public VK wall/Dzen article forms; reject login/editor/shortener URLs, embedded credentials, fragments/tracking/query ambiguity, wrong provider, mismatched account identity where locally verifiable, and conflicting object IDs. Do not fetch or follow a URL; no SSRF surface. Dzen object-to-account linkage not locally provable remains explicitly Owner-attested rather than provider-verified.
- Commit requires exact preview envelope hash, current manifest checksum, idempotency key and expected fact digest/null. Re-read every binding under the transaction; stale digest/role/tenant/channel/custody blocks with a specific reason and fresh-preview action. Identity lock key is scoped to project+provider+canonical object; concurrent commits to one object across different tasks cannot both create facts.
- Create the canonical published fact with confirmation_mode=manual, evidence retaining the authenticated Owner confirmation reference and explicit origin/time basis. In the SAME transaction append a versioned manual-confirmation WorkflowEvent referencing fact ID and exact fact digest, object identity, previous/current fact state, current revision observation, published revision binding, manifest and custody digests, timestamp precision and confirmation reference. Versioned audit is provenance, not a parallel publication table. No schema migration proposed.
- Exact replay returns the same fact/audit result, zero repeated checkpoints or state changes. Same key with different envelope conflicts. Existing different fact needs Owner correctionReason plus exact expected fact/provenance digest, appends a new provenance event, and preserves all prior audit. No blind overwrite or downgrade from manual to automatic authority. A conflicting object bound to another task is a denied reassignment, not an implicit correction.
- Update the existing canonical task publication projection and ordinary metric checkpoints using shared FactService policy, making manual origin/revision binding visible in task/fact responses. Preserve accepted text/assets/approvals and all old delivery attempts, connector jobs/generations/bindings/receipts, leases and work-item states byte-for-byte. In particular generic browser-work completion is suppressed for this transition; no fake worker completion, lease revocation, generation bump, provider receipt, delivered attempt or connector confirmation.
- A manual fact becomes a no-new-send fence, not recovery permission. Every affected release/claim/start/submit/confirmation route must refuse a new mutation after the manual fact or preserve it on replay. Late callbacks cannot overwrite it, turn old UNKNOWN into delivered, or treat an Owner-asserted timestamp as native proof. Already issued external requests cannot be retroactively cancelled; the accounting result must not claim that they were.
- Existing site/action/provider denials remain effective. This surface performs only internal manual accounting, never invokes the denied provider operation, adapter control, browser, reader or executor. It is not a direct/API/browser fallback for Dzen/VK publication. No resend, adapter activation, job adoption or route permission is granted.

## Measurable QAR026

- Zero provider/network/browser/credential-resolution calls on preview, success, refusal and replay. Test at actual MCP boundary and with network-disabled containers.
- Atomic owner/tenant/fact/provenance/projection/checkpoint transaction: actual PostgreSQL fault injection at each write boundary rolls back all changes. No mixed partial results.
- DB statement timeout20s, lock timeout5s, whole invocation deadline30s. At most one commit attempt; serialization/timeout/ambiguous commit yields readback/reconciliation guidance, never automatic retry with a fresh key. Preview and request payload capped64KiB, evidence reference capped2048 characters. No bulk mutation; one task/object per commit.
- Actual concurrent submissions same task/key and same object/different tasks: one canonical authority; exact replay has zero additional fact/audit/checkpoint rows. Correction CAS tested independently.
- Zero changes to accepted content, images, decisions, prior attempts/jobs/work/leases/history under success, failed audit and late callback. Compare full persisted row snapshots, not just status counts.
- No new any, silent catches, runtime debt findings or blanket baseline exemptions. New cohesive modules below400 lines; no substantive growth of existing FactService god module without a decomposition decision. Mandatory quality gate, focused boundary/PG suites and backend/frontend builds.
- Safe error result includes stable code, concrete reason, supported correction, retry_allowed=false; raw exceptions, headers, tokens, signed URLs, full provider payloads and content bodies are absent from logs/responses.

4. 5. Keep code independent of task/project/account/revision business IDs. Case identifiers below are input evidence only, never imported as executable production authority. Owner confirmation provides no blanket exception to accepted-package rules of automatic delivery.

## RISK026 and adversarial review

High reliance: an incorrect fact hides delivery debt or binds the wrong publication, while an unsafe recovery can cause duplicates. Owner assertion is an explicit trust decision, not provider verification. Distinguish fact existence, exact edition binding, manual time and unresolved old transport in readbacks.

Threats to cover after lock approval: forged actor/profile, demo/role revocation race, cross-tenant task/channel, manipulated preview, stale manifest and changed approval/body, duplicate URL aliases, same object on different tasks, fabricated attempt, ambiguous legacy custody, correction replay, audit failure, lease/permit race and late callback overwrites, imported plan reintroducing debt, fake provider success, timestamp fabrication, credential-bearing references and error/log leakage. Owner input cannot weaken another aggregate's ownership or create publisher execution authority. Do not relax admission flags, write transport delivered states or use SQL fact insertion to avoid these guards.

MVP bound: VK posts/Dzen articles only; manual provenance is explicit; no platform fetches, body scraping, edits, resend, duplicate consumer, correction of publication approvals or historical delivery certainty. An unsupported custody/projection discovered during implementation is a design finding, not permission to hard-code the three cases.
