# Approved Owner command acceptance

Human architecture approval preceded test creation. Operator surface: Owner MCP creates one explicit instruction; existing sole Publisher consumes normal claim/start/pre-submit/confirm controls. No provider transport is added.

1. UNKNOWN and duplicate: ordinary pre-submit rejects old uncertain attempt; Owner orders an additional publication; fresh current manifest is accepted as a new authorization, not an edit of the old release; new numbered attempt permits duplicateAbsent=false and records its actual fact; old UNKNOWN row stays byte-for-byte unchanged.
2. Replay: same Owner command returns the same work; same permit key never permits again; different send key cannot enlarge the instruction.
3. Privilege: Publisher with project-owner actor cannot mint an instruction. Foreign actor, demo account and revoked Owner membership cannot mint authority. Issuing Owner membership/demo status is also rechecked during consumption.
4. Atomicity: preview changes nothing; package mismatch creates no authority; audit failure rolls back task, new work and cancellation of prior work.
5. Concurrency: racing identical commands create at most one new work and immutable instruction; conflict can be reconciled by the original key without another human GO.
6. Existing recovery: persisted old recovery hold does not veto explicit Owner instruction; same registered default preparation/start entry executes new work; fact writes retain the original hold unchanged.
7. Scope drift: changed approval on replay conflicts; changed accepted body rejects a stale package. Old work/lease cannot pre-submit after the new instruction.

Regression boundary: existing shared-browser release/execution/confirmation/fences/diagnostics/text-only/MCP, real PostgreSQL lifecycle/recovery/preparation and compiled actionable diagnostic tests. No mocks establish a real provider send, production deploy or Owner UAT.
