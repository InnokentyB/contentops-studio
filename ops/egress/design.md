LOCK: reduce repeated settings reads, MCP authentication payload/writes and redundant full logical backups without weakening tenant/auth/publication controls. Investigation is read-only; no runtime implementation, tests, public release or production policy changes authorized by this document.

ARCH settings: first identify exact hot keys/current callers on current deployed source. Allowlist only non-authoritative configuration for bounded per-project/key process cache, proposed60s TTL, max1000entries, single-flight, defensive snapshots. No auth, secrets, release approvals, accepted content/manifests or work/recovery state caching. After successful transaction commit invalidate affected local entry and discard in-flight stale fills using generation marker. Other service instances bounded byTTL, explicitly not immediate global invalidation. Settings needing strict fresh semantics bypass cache. Fresh bypass supported internally, not untrusted caller authority. DB error never serves expired settings. Eviction/TTL memory bounded.

ARCH MCP: no positive authorization TTL until a separately approved bounded revocation contract exists. Preserve DB checks of token/profile/expiry/revocation/current membership at authorization boundaries. Reduce selected fields; combine lookup/membership where supported without exposing token hash. Coalesce concurrent duplicate checks only within one request, not across requests. Propose conditional last_used_at update at most once per credential per60s across processes (DB time predicate), select no token/secret fields in update result. last_used_at becomes coarse operational timestamp, not per-call audit. Revocation/role tests remain immediate. Exact implementation needs source+transaction review before scenarios.

ARCH backups: proposal RPO24h for routine backups, full logical backup daily at most unless destructive/data migration needs exact pre-change snapshot; no persistent scheduler activation yet. Ordinary code-only releases may reuse same database-bound verified archive younger24h if schema compatible and no data migration/destructive action. Check private archive SHA, restore-verification receipt, server/db binding and schema migration ledger, not whole-table hashes or rowcounts as proof of no changes. Routine writes mean archive is older recovery point; reuse does NOT assert unchanged database or lossless rollback. Single-process/distributed execution lock needed before scheduling concurrent operators; durable receipt and fail-closed mismatch; explicit force reason for exceptional new full backup. Code rollback preserves DB. Retain all current backups until separate retention review.

Incremental option: pg_dump custom-format is full logical backup, local binary diff cannot lower downloaded bytes. Physical basebackup+WAL or platform PITR is distinct supported architecture; access/retention/restore availability on Supabase Free not established. No homegrown updated_at delta: misses deletes, sequences, DDL and transaction consistency. Investigate supported provider PITR/replication later before choosing paid plan or infrastructure migration; no subscriptions/settings changed.

QAR: settings100concurrent same-key reads require1DBload; repeated liveTTL reads require0additional DBloads; cacheexpiry/write/racingfill/tenant separation explicit. MCP revoked token/membership denied on next authorization boundary, no cached permissions; last_used write at most1per60s under concurrent processes. Backup reuse produces0DBdumpbytes, bounded metadata reads only; newarchive must restore in isolated Docker. Changes need failing acceptance first, focused/integration/build/quality, owner UAT. Savings claims only after measured before/after comparable window, not pg_stat rowcounts alone.

RISK: stale settings limit60s only where product tolerates; no broad Prisma interception. No raw credentials/SQL/results in telemetry. No simple Redis authorization cache without invalidation/failure contract. Backup24hRPO is product choice needing explicit approval; no removal of fresh-backup safety gate before approval. No production flag/worker/provider/schedule changes in local package.
