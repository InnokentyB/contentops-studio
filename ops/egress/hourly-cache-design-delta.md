# LOCK/QAR/ARCH/RISK delta: one-hour coordinated settings cache

Owner requests one-hour prompt/model cache and immediate coordinated invalidation after save. "медленный" is interpreted as typo for the prior agreed immediate invalidation. This supersedes only the60s process-local settings cache; MCP usage60s and24h backup RPO remain unchanged. No implementation/scenarios before approval of this substantive cross-process design.

LOCK: ordinary generation prompt/model keys only; DB authoritative. After a successful save acknowledgement, subsequent reads in both web and MCP use the saved value. No scheduled hourly DB fetch; lazy cache miss after1h. No caching of tokens/rights/accepted content/publication state.

ARCH: use existing ioredis dependency via dedicated lazy client, not src/queue import (that creates BullMQ queues). Existing Redis settings reused; no credentials/logged URLs, no new queue consumer or provider worker. Shared revision metadata and1h data cache must use atomic Redis scripts to fence stale fills. A simple publish/subscribe notification alone is insufficient because lost events can preserve stale values for an hour.

Write path: persist settings plus a durable invalidation event in the SAME PostgreSQL transaction using existing outbox_events. Use a dedicated event_type and ensure existing generic outbox consumers cannot consume/mark these delivered. Complete Redis invalidation before reporting an ordinary successful save; if DB committed but invalidation is uncertain, explicitly return saved-but-cache-sync-pending rather than suggest repeating a provider action. Pending events are retried by a bounded cache-only delivery loop, never external publication. A persistent pre-write barrier prevents cache fills while an update is in progress; concurrent writers tracked independently. Failed process/Redis restart cannot be treated as proof all writes completed. Unresolved barrier or event forces direct DB reads, not hour-old data. No self-issued stop receipt or manual flag can establish data freshness.

Failure contract: Redis unavailable -> bypass cached reads and use DB. If coordination cannot be established BEFORE a cacheable settings write, refuse it with a precise temporary synchronization error and corrective action; do not silently save while another replica may retain old data. DB-committed writes with pending invalidation stay recoverable through the durable event. Startup/reconnect requires clearing/reconciling local state and pending delivery before cache readiness; command timeouts and shutdown cleanup explicit. No paid service or production activation included.

QAR: two actual processes using synthetic PostgreSQL/Redis; after acknowledged save next other-process read is fresh; pending old load cannot repopulate;100same-key callers single-flight; one-hour expiry lazy; tenant isolation and credential bypass; process death between commit/invalidation and Redis disconnect/restart tested; no cache hits while synchronization uncertain; all pending work bounded. Low-volume metadata/event delivery traffic measured separately from heavy setting values, no false zero-DB claim.
